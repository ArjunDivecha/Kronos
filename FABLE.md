## 1. Assessment

The fork is a competent, fast-moving research layer with one genuinely careful change and a cluster of
research-hygiene liabilities. Honest read:

**What's good.** The one functional edit to the model is the right one: temporal-leakage guards in
`KronosPredictor.predict`/`predict_batch` (`model/kronos.py:561-578`, `:654-676`) reject non-monotonic
timestamps and any case where the context window's end is not strictly before the forecast window's start.
For a quant fork whose whole value depends on no look-ahead, adding this at the model boundary is exactly
where it belongs. The live trader (`industry28_trader.py`) is also more defensive than typical: dry-run
returns before order submission (`:555-557`), orders require a literal `YES` (`:563-564`), abort writes
nothing (fixed in `fdd5bca`), and `sample_count=20` + `torch.manual_seed(42)` (`:313`, `c0b8ccd`) make the
signal deterministic run-to-run. Docstrings were added throughout `model/` without touching logic.

**What's risky.** The research scripts that produce the Sharpe/IC numbers justifying real trades have three
systemic weaknesses:
1. **Silent failure.** `etf_strategy.py:165-166` is a literal `except Exception: pass  # skip malformed
   batches silently`; `run_industry28.py:208`, `broad_oos_test.py:166`, `etf_sweep.py:222` print-and-continue.
   A malformed batch silently drops its tickers from the cross-section, biasing every downstream metric. This
   directly violates the repo's own FAIL-IS-FAIL rule.
2. **Caches without invalidation.** Every walk-forward script loads `forecasts_*.csv` if the file exists
   (`run_industry28.py:406-409`, `etf_strategy.py:290-292`, `broad_oos_test.py:281-283`) with no check that the
   cached tickers/lookback/pred_len/model match the current config. Tweak a parameter, rerun, and you silently
   report stale results.
3. **Comparability + leakage hazards.** `etf_sweep.py` and the tests use `Kronos-small` while every other
   script uses `Kronos-base`, so cross-script Sharpe/IC comparisons are apples-to-oranges. The hardcoded OOS
   cutoff `2024-07-01` (`run_industry28.py:259`) is asserted as out-of-sample without evidence it post-dates
   Kronos's pretraining window; survivorship bias is uncontrolled in `broad_oos_test.py`'s literal ticker
   lists. None of these are code bugs — they are validity risks that make the numbers softer than they look.

**Test/infra.** One test file, not hermetic: no `conftest.py`, `from_pretrained` called live, so `pytest`
errors (not skips) without HF Hub access. ~153 MB of `forecasts_*.csv` are committed to git. The live trader
carries a Python-3.14 event-loop shim (`:73-79`) but the venv is 3.9.6.

Bottom line: the trading path is careful; the evidence-generation path is not, and that is the higher-value
place to harden because it is what tells Arjun whether to keep trading real money.

## 2. Prioritized improvements

### P0 — Make batch inference fail loudly (authored as the contract in §3)
- **What & why:** replace the silent `except: pass` / print-and-continue in the walk-forward loops with
  fail-loud-or-record behavior, so a dropped series is impossible to miss. Evidence: `etf_strategy.py:165-166`,
  `run_industry28.py:208`, `broad_oos_test.py:166`, `etf_sweep.py:222`.
- **Bet:** *if* a run has ≥1 per-series inference error, *then* it exits nonzero or records every dropped series
  in a manifest and never silently writes a shrunken frame; *observable:* an injected-failure fixture exits
  nonzero or emits a non-empty manifest naming the bad series (today it exits 0 with the series silently gone).
- **Invariants:** no error discarded without abort-or-record; `requested == succeeded + failed`; live trader and
  `model/` untouched.
- **Gate intent:** run the backtest on a fixture with one malformed series; require nonzero exit OR a manifest
  naming it, and `requested == succeeded + failed`.
- **Effort:** ~half a day (shared helper + one fixture + patch four call sites).

### P1 — Cache invalidation by config fingerprint
- **What & why:** stamp each `forecasts_*.csv` (or a sidecar) with a hash of `{tickers, lookback, pred_len,
  stride, model_id, date_range}`; on load, recompute (or error) if the fingerprint mismatches. Evidence:
  `run_industry28.py:406-409`, `etf_strategy.py:290-292`, `broad_oos_test.py:281-283`.
- **Bet:** *if* the cache was produced under a different config, *then* the loader refuses it; *observable:* a
  test that writes a cache under config A and requests config B does not silently reuse A.
- **Invariants:** a served cache's fingerprint equals the requested config's fingerprint; no config change is
  ever silently ignored.
- **Gate intent:** fingerprint-mismatch fixture forces recompute-or-error, not silent reuse.
- **Effort:** ~half a day.

### P2 — Unify model choice and pin revisions across the research scripts
- **What & why:** `etf_sweep.py:128` uses `Kronos-small`; the rest use `Kronos-base`, and only the tests pin a
  HF revision. Centralize `MODEL_ID` + `REVISION` in one module and import everywhere so results are comparable
  and reproducible.
- **Bet:** *if* two scripts report IC for the same universe, *then* they used the same model+revision;
  *observable:* a grep/test asserts a single `from_pretrained(MODEL_ID, revision=REV)` source of truth.
- **Invariants:** exactly one model id and revision constant referenced by all research scripts.
- **Gate intent:** a test greps for stray `from_pretrained("NeoQuasar/...` literals and fails if any script
  bypasses the shared constant.
- **Effort:** ~1-2 hours.

### P2 — Repo hygiene: stop committing ~153 MB of forecast CSVs
- **What & why:** the `forecasts_*.csv` outputs (up to 24 MB each) are checked in and re-committed on each run,
  bloating history. `.gitignore` already ignores `*.parquet`/`*.h5` but not these CSVs.
- **Bet:** *if* outputs are gitignored and stored as parquet, *then* `git status` after a backtest shows no
  multi-MB text diffs; *observable:* repo `.git` growth per run drops to ~0.
- **Invariants:** no generated `forecasts_*.csv` is tracked after the change.
- **Gate intent:** `git ls-files | grep forecasts_.*\.csv` returns empty.
- **Effort:** ~1 hour (plus a one-time history decision — leave history alone, just stop the bleeding).

## Context

Repo root: `/Users/arjundivecha/Dropbox/AAA Backup/A Working/Kronos/shiyu-coder-Kronos`. This is Arjun's
fork of the Kronos financial candlestick foundation model, with an added quant research + live-trading
layer. Several walk-forward backtest scripts run batched Kronos inference over many tickers per date and
then rank the cross-section to build long/short portfolios whose Sharpe and information-coefficient (IC)
numbers are used to justify a live IBKR strategy (`industry28_trader.py`, which is OUT of scope here).

The defect: the batch-inference loops swallow errors. `etf_strategy.py:165-166` is a literal
`except Exception: pass  # skip malformed batches silently`; `run_industry28.py:208`, `broad_oos_test.py:166`,
and `etf_sweep.py:222` print and continue. When a batch raises, its series vanish from the output frame with
no record, silently shrinking the cross-section and biasing every downstream IC/Sharpe number. This violates
the repo's own FAIL-IS-FAIL rule (`~/Dropbox/AAA Backup/CLAUDE.md`).

Terms: "series" = one ticker's forecast task for a given as-of date; "failure manifest" = a machine-readable
file (e.g. CSV/JSON) listing each dropped series id and the exception reason; "requested" = the count of series
handed to the inference loop for a run. The Build-Mode agent must discover the real entry points among the four
scripts above and pick at least the primary one (`run_industry28.py`) plus `etf_strategy.py` as `scope.in`.

## Build Loop vs Product Loop

The build loop can prove, with a deterministic fixture that injects one malformed series, that the backtest
either exits nonzero or emits a failure manifest naming that series, and that requested == succeeded + failed
(INV1, INV2), while leaving the live trader and model internals untouched (INV3). That is all the machine gates
prove. The product bet — that removing silent drops materially changes the reported IC/Sharpe and therefore the
real trading decision — can only be judged by re-running the full backtests on real data and comparing metrics,
which happens outside this contract. The coding model may not claim the product bet is satisfied solely because
the gates pass.
